# InfrSync: Advanced Blockchain & Enterprise Roadmap

This document outlines the expanded and refined strategy for integrating enterprise-grade blockchain capabilities into InfrSync. It builds upon the core architecture by introducing crucial bridging layers (Oracles) and decentralized storage optimizations.

---

## 1. Smart Contract Architecture (Solidity)

The primary ledger will be deployed on a Layer 2 network (such as **Polygon** or **Arbitrum**) to ensure high throughput and negligible gas fees, making it sustainable for government operations.

### Core Data Structures
*   **Bidder Registry (`mapping(address => string)`):** A dedicated mapping that links Web3 wallet addresses to verified Company Registration Numbers. This acts as the on-chain KYC layer.
*   **Tender Struct (`Tender`):**
    *   `tenderId` (uint256): Unique identifier for the Road Project.
    *   `aiPredictedCost` (uint256): The baseline cost generated by the ML model, fed into the blockchain via an Oracle.
    *   `officialAddress` (address): The specific Government Official wallet managing this tender.
    *   `isOpen` (bool): Status of the tender.
*   **Bid Struct (`Bid`):**
    *   `bidderAddress` (address): Who submitted the bid.
    *   `bidAmount` (uint256): Total proposed cost.
    *   `dataHash` (string): **CRITICAL INNOVATION:** An IPFS CID (Content Identifier) containing the granular form data (Material cost, Labor, Timeframe). This keeps gas costs incredibly low while ensuring the detailed bid cannot be secretly altered.
    *   `isValid` (bool): Set exclusively by the AI/System Oracle (ensuring the bid falls within the 97-100% acceptable range of the predicted cost).

### Logic Flow & Lifecycle
1.  **Creation:** The Gov Official publishes a Tender. The ID and AI-predicted cost are etched on-chain.
2.  **Submission:** A Contractor signs a transaction via MetaMask. Their comprehensive bid details upload to IPFS, and only the `dataHash` and `bidAmount` are sent to the contract.
3.  **Validation:** The off-chain API (FastAPI) triggers the ML evaluation. The AI Oracle pushes a transaction to the contract updating the `isValid` flag for that specific bid.
4.  **Selection:** The Official calls `awardContract()`. The contract implements a `require(bids[chosenId].isValid)` to ensure no invalid bid can ever be selected by human error or corruption.

## 2. Technical Stack Expansion

To achieve this robust architecture, InfrSync will utilize a carefully curated stack:

| Component | Technology | Purpose |
| :--- | :--- | :--- |
| **Blockchain** | Solidity / Hardhat | Smart contract development, testing, and deployment. |
| **Decentralized Storage** | IPFS (via Pinata) | Securely stores heavy bid documents (PDFs, detailed CSVs) and returns the lightweight `dataHash`. |
| **Oracle Layer** | Custom Web3.py Script | Acts as the secure bridge. The FastAPI (XGBoost) backend evaluates bids and uses Web3.py (funded with a dedicated backend wallet) to push the "Valid/Invalid" status to the Smart Contract. |
| **Contract Security** | OpenZeppelin | Industry-standard, audited contract templates for strong Role-Based Access Control (RBAC) like `onlyOfficial` modifiers. |

## 3. Implementation Steps

The integration will be executed in four distinct phases:

- [ ] **Phase 1: Smart Contract Development**
  - Write `RoadRegistry.sol` and `TenderSystem.sol`.
  - Implement robust access control using OpenZeppelin modifiers (`onlyOfficial`, `onlyRegisteredContractor`, `onlyOracle`).
  - Write Hardhat unit tests to simulate the entire bidding lifecycle.
  
- [ ] **Phase 2: The Oracle Bridge (Backend)**
  - Update the `api.py` (FastAPI) to include `web3.py`.
  - Securely manage a "Backend Oracle Wallet" private key using environment variables (.env).
  - Create the endpoint that takes the ML evaluation and automatically sends an Ethereum transaction to update `isValid` on-chain.

- [ ] **Phase 3: Frontend Web3 Integration**
  - Integrate `wagmi` and `viem` in the Next.js application.
  - Add a unified "Connect Wallet" (MetaMask) button that functions alongside the existing Web2 NextAuth login.
  - Implement the flow where submitting a bid first uploads data to Pinata (IPFS), gets the hash, and then prompts MetaMask to sign the blockchain transaction.

- [ ] **Phase 4: Transparency Dashboard**
  - Create a public "Audit & Transparency" page.
  - Anyone (the public, journalists, auditors) can enter a Tender ID to view the full, immutable history: Who originally bid, which bids were marked valid by the ML model, and who the official selected as the winner.

## 4. Security & Compliance Strategies

- **Non-Repudiation:** Once a government official signs the `awardContract()` transaction, their cryptographic signature is inextricably tied to that choice forever. They cannot deny approving that specific contractor.
- **Oracle Integrity:** The Oracle wallet (Backend API) is the only address permitted to change the `isValid` boolean. This prevents malicious actors or regular officials from overriding the AI's safety checks.
- **Hybrid Data Privacy:** Personal contact information (Phone numbers, emails, names) stays securely in the Web2 MongoDB database. Only project-related financial numbers, wallet addresses, and IPFS hashes are pushed to the public Blockchain.
